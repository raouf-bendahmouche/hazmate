# Full Project Explanation: Hazardous Material Transport License Management System

## 1. What Problem the Application Solves

The Hazardous Material Transport License Management System exists to manage a compliance-heavy workflow that cannot be left to memory, paper folders, or loosely organized spreadsheets. The domain is administrative but the consequences are operational: licenses expire, vehicle and carrier information must stay aligned, route records must be traceable, and deleted records still need to be recoverable for audit or correction. The application solves that by turning the contract lifecycle into a structured local desktop system with a clear data model, repeatable validation, and a visible operational dashboard.

The important thing to understand is that this is not just a CRUD app. The user is not entering isolated records. A single contract ties together a company, vehicle, route, possible hazardous material record, and audit history. The system therefore has to do more than store fields. It has to coordinate several related entities in a controlled order, keep those records searchable, preserve historical data through soft delete, and make the current state easy to inspect at a glance. That is why the application is organized around a service layer, a validation layer, a database layer, and a local desktop shell rather than around direct UI-to-database calls.

## 2. How the System Works End to End

When the user starts the application, Electron is the outer shell that launches the Python backend and waits for it to become ready before the interface is used. That startup synchronization matters because the frontend is only a client of the backend API; it does not own the data and it does not talk to SQLite directly. Once the backend is listening, the UI renders the dashboard, loads the current statistics, and begins showing contract state, expiration data, and search results.

When the user creates a new contract, the frontend collects the form data from one unified entry screen and sends it to the local API using the frontend API client. The API receives the request, validates the payload with Pydantic, checks for duplicates, and then delegates the real workflow to the license service. The service takes responsibility for the contract as a business object: it validates business rules, finds or creates the related company, finds or creates the vehicle, creates the route, optionally creates a hazardous material record, writes the license, and finally records an audit entry. That sequence is important because the user is really creating a network of related records, not just a single row.

After data is stored, the backend becomes the source of truth for every subsequent view. Search pages query the API, which reads from SQLite and returns structured JSON. The dashboard requests aggregate statistics, and the backend computes them from the same database while preserving cache boundaries so repeated reads stay fast. Background jobs also run inside the backend process to check for expirations and to keep operational data up to date. The result is a system that behaves like a desktop application from the user’s point of view but still keeps strong separation between presentation, business rules, and persistence.

## 3. How Data Moves Through the Architecture

The architecture is a local N-tier desktop design. The frontend is the presentation tier, Electron is the process host and startup manager, FastAPI is the HTTP boundary, services are the orchestration and policy tier, and SQLite is the persistence tier. This structure is deliberate. The frontend needs to stay lightweight and responsive, so it renders views and gathers input. The backend needs to stay authoritative, so it owns validation, business logic, and database mutation. The database needs to stay simple and reliable, so it stores normalized records and exposes a stable schema.

A typical request begins in the frontend controller. The JavaScript layer collects user input, packages it into JSON, and sends it over HTTP to the local API. The API layer validates the shape of the data and applies request-level checks such as duplicate detection or simple range limits. If the request is valid, the API passes it to a service module. That service may consult the business rules engine, perform lookups, create dependent records, or call into the database wrapper. The database wrapper opens a fresh SQLite connection, applies the right pragmas, executes the write or read, and returns the result. On the way back up, the backend formats a stable JSON response, and the frontend uses that response to update the DOM or navigate to the correct page.

This flow is repeated for search, restore, statistics, settings, and health checks. The only difference is the shape of the work being done in the service and database layers. Search is read-heavy and uses filtering and pagination. Statistics are aggregation-heavy and often cached. Restore is policy-heavy because the system must ensure the related records still exist before reviving a deleted license. Settings are simple key-value persistence. The architecture keeps those paths distinct so each one can evolve without forcing changes everywhere else.

## 4. Major Modules and Their Roles

The frontend is responsible for what the user sees and how the user navigates. `frontend/index.html` defines the page shell, `frontend/css/style.css` controls the look and layout, `frontend/js/main_dashboard_controller.js` manages page routing and UI state, and `frontend/js/frontend_api_client.js` provides the only supported path from UI code to the backend. The frontend is intentionally not allowed to reach directly into the database because doing so would collapse the architecture and make validation impossible to centralize.

The backend API is the HTTP contract between the desktop shell and the domain logic. `backend/api/api_endpoint_manager.py` defines the FastAPI app, routes, request models, error handlers, and startup lifecycle hooks. It acts as a thin edge layer rather than a place to hold business rules. That choice keeps the API readable and keeps the real application behavior in the services where it belongs.

The services package contains the real business workflow. `services/license_service.py` coordinates multi-entity contract creation and lifecycle changes. `services/business_rules_engine.py` centralizes policy checks. `services/statistics_service.py` computes dashboard data and provides a cache so the dashboard can be refreshed without rerunning expensive joins every time. `services/background_job_manager.py` and the notification helpers keep backups and email-related side effects separated from the main request path.

The database layer stores the application state and keeps the schema stable over time. `database/schema_definitions.sql` defines the tables and relationships, while `database/connection_handler.py` manages connections, retries, migrations, cache invalidation, and soft-delete operations. This layer matters because local desktop applications often fail not from lack of features but from poor handling of persistence details such as locking, schema drift, or accidental deletion. The wrapper in this project is deliberately opinionated so those problems are handled consistently.

Electron is the runtime shell that makes the project feel like a desktop application rather than a browser tab pointing to a local web server. `electron/main.js` starts the backend process, waits for readiness, and then allows the renderer to operate. That startup sequence is important because the app depends on the backend being fully available before the UI can function safely. Without that handshake, the frontend would race ahead of the server and produce unstable behavior.

## 5. Why the System Is Organized This Way

This project is built around separation of concerns because the domain itself is multi-step and compliance-sensitive. A direct UI-to-database design would be faster to write initially, but it would make the application much harder to reason about once contract creation, soft delete, restore, audits, notifications, and dashboard analytics all need to work together. By using a service layer and an explicit API boundary, the system keeps each responsibility narrow and easier to test.

The choice of Python and FastAPI is practical. Python is well suited to validation, database orchestration, and background jobs, and FastAPI gives the backend a typed, expressive HTTP layer with clean request models. SQLite is also a pragmatic fit because the application is local-first and does not need the deployment complexity of a server database just to support a desktop compliance tool. Electron supplies the desktop packaging and process lifecycle management while allowing the UI to be built with familiar web technologies. The combination is not accidental; it is a minimal stack that still supports a clear boundary between presentation, logic, and storage.

The project is also organized to make future maintenance survivable. The docs explain the architecture, the services isolate the core logic, the connection handler protects the database, and the UI controller centralizes rendering and navigation. That means a new developer can learn the system in layers instead of having to reverse engineer everything from the top-level screen. It also means changes like restoring the single-window Add Contract flow can be localized to the frontend controller without forcing structural changes across the rest of the app.

That is the deeper point of the architecture: the system is not just working code, it is a maintainable shape for a compliance workflow. The design makes the application understandable, the modules keep responsibilities separate, and the data flow keeps the contract lifecycle consistent from user input to database record to dashboard insight.
